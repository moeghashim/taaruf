# Website interest flow and all-origin final contact gate

Review-only implementation for issue #64, stacked on the PR #61 security/photo candidate. Not deployed.

1. A female-origin submission remains private.
2. An admin selects **Share requester profile** to create a recipient-specific review link. The intended brother receives a notification inside his authenticated portal and one generic review-invitation email queued in the existing outbox; no manual messaging is required. Existing eligible private female submissions can enter this workflow through this explicit admin action, without inferred photo or relationship consent.
3. The brother signs in and explicitly accepts or declines. Merely opening a link changes nothing. Acceptance queues a sister confirmation email.
4. The sister explicitly confirms on the website. This atomically creates exactly one mutual match, pending final admin approval, and queues an independent pending-review email for each applicant.
5. Final admin approval makes contacts available in both authenticated portals and queues each applicant a contacts-ready email containing only the portal link. Contact data is never included in these emails.

## All-origin final approval (expanded issue #64)

This supersedes earlier preserve-male-policy claims for **final contact release**. Male inbound discovery and reciprocal discovery remain unchanged; neither is final consent. Male-origin and linked reciprocal flows now record explicit participant approvals, reuse/create one reviewing match, and queue two pending-review deliveries. Only authenticated final admin approval releases contacts and queues two contacts-ready deliveries. Reciprocal approvals are mirrored by participant identity, not requester position. Mirroring approvals and joining the pair never publishes an unshared private female review or its photos; explicit admin sharing remains a separate access boundary, even after both approvals or contact release. Legacy pending flows use this gate on their next action; historically disclosed contacts are retained without migration/backfill.

Female-origin admin, email, WhatsApp and platform interests use the same authenticated review workflow. Pair approvals are scoped to the event and actual participant identity; reciprocal submissions do not grant approval. Both paths reserve participants against other active pending or released matches in the same transaction. Both paths share the existing durable outbox, cooldown, leases, immutable payload and provider idempotency machinery (legacy table/environment names retained). Pending-review deliveries remain independently deliverable after admin release. Admin status updates to contact_shared invoke the same privileged release transaction as the share-contacts route, never a bare status patch.

## Delivery and operational gates

Email delivery records are transactional per interest, stage and recipient. The worker uses leases, immutable provider payloads and stable provider idempotency keys. Retry-After applies across workers. Uncertain attempts beyond the provider deduplication safety window require manual reconciliation, not blind retries. Failed records are separately visible in the admin inbox and can be retried without repeating consent actions, including while the match is paused. Closed, declined, revoked and reset workflows remain unavailable; the provider idempotency window still applies and successful recipient deliveries are not resent.

The `brother_review` invitation is enqueued atomically by authorized `createReview`, only when the resulting state is `awaiting_brother_review`. The existing interest/stage/recipient key deduplicates double clicks and token reissues, including after successful delivery or failure; reissue does not reset a delivery. Reads do not enqueue and there is no backfill. Both claim and pre-send authorization require the intended brother, a valid unexpired review, and an active approved pair; accepted/declined/revoked/closed/reset reviews cannot receive a stale invitation. The subject is “A profile is ready for your review”; the body contains only generic sign-in instructions and the authenticated dashboard destination, not a bearer token, name, applicant number, photo or contact data. Existing retry, cooldown, lease and immutable-payload behavior is reused without a second queue. As with existing notifications, revocation after the final pre-send check cannot recall an in-flight email; the linked portal still enforces current authorization.

Delivery is disabled by default. Isolated delivery requires an explicit recipient allowlist and non-production portal. Future **brother-review-only** production delivery requires `FEMALE_WORKFLOW_EMAIL_MODE=brother-review-production`, `FEMALE_WORKFLOW_PRODUCTION_APPROVED=true`, an exact approved HTTPS portal origin, and dedicated sender/provider settings. Required dedicated settings are `FEMALE_WORKFLOW_RESEND_API_KEY`, `FEMALE_WORKFLOW_EMAIL_FROM`, and `FEMALE_WORKFLOW_PORTAL_URL`; isolated mode additionally requires `FEMALE_WORKFLOW_EMAIL_ALLOWED_RECIPIENTS`. Source diagnosis: missing settings, disabled/unset mode, a disallowed recipient/origin, or missing production approval cause `deliveryConfig` to return null and the row to fail before any provider request. A successful share means the portal review exists, not that email was queued or delivered. Missing activation/configuration records a non-backfillable failed notification. See [future-only activation](pr87-future-only-activation.md) for the mandatory one-time activation boundary and owner setup. Shared `production` mode is NOT authorized for this rollout. The existing one-minute cron drains the outbox. This is a source-based diagnosis, not a claim about current deployed environment values. None are enabled by this change; owner approval/configuration remains a release prerequisite. Never point a preview at live applicant data. Vercel previews without verified isolated configuration disable API access and are UI-review-only.

## Applicant notification destinations

New general-interest notifications and final-approval requests use `/me?connection=<interestId>`. Female-review invitations and workflow deliveries use `/dashboard?femaleReview=<interestId>`; pending-review and contacts-ready deliveries use the destination for their originating workflow. Requested connections and selected reviews are resolved through authenticated participant-scoped lookups independently of bounded history lists. Selected review decisions and Pause/Resume controls use that authorized lookup and refresh after a successful action.

Signed-out or expired sessions preserve the selected destination through `/login?next=...`, the login request, and `/api/applicant/login/verify?token=...&next=...`. Each server boundary validates the destination: only `/me` with a `connection` ID or `/dashboard` with a `femaleReview` ID is retained, with `/me` as the fallback. External, protocol-relative, backslash, encoded and malformed destinations are rejected; extra parameters, including review bearer tokens, are not forwarded. Login never bypasses participant, lifecycle or capability-cutoff authorization.

## Pause, resume and privacy

Pause remains supported with authenticated Resume in the admin match/workbench and applicant portals. A paused match retains its decisions, source, event, photo permissions and disclosure history. Resume checks both participants for intervening active matches; pending matches still require final admin contact release. Resuming released history preserves the first disclosure and queues no additional emails. Closed, declined and reset records cannot resume.

Brother-facing review and connection identities remain neutral before initial acceptance. Under name4436 / Omar4449 approval, the exact authenticated inbound female review and connection card show only the first whitespace-delimited name token after persisted brother initial acceptance, including existing accepted interests. Both a valid persisted acceptance timestamp and exact flow recipient acceptance are required; final approvals or contact release alone do not grant a name. A valid unexpired review and active approved participants are required. Archive/restore, revocation, reset, closure, invalid linkage and unrelated interests fail closed. Surname, photo and contact gates are unchanged; reciprocal/outbound grants are not widened. Owner and admin names remain visible. Public submission and final-approval results contain no notification recipient name/email; the server-authorized notification query owns those details. Newly frozen delivery links follow the [applicant notification destinations](#applicant-notification-destinations). Previously attempted immutable mail cannot be recalled or rewritten. Existing released email/phone visibility remains unchanged.

The interest list has one view with derived lifecycle and approval labels, including paused records. Manually editable active/queued priority, matched/requested tracking and Progress/Convert controls are removed. **Share contacts** appears only for an eligible approved pair with a valid match and asks for confirmation of final admin release; the server rechecks both participant approvals and audits disclosure. Notes, unshared decline/close and test reset remain available. This source-only review does not deploy, publish, change Git identity or create human certification.
